# External crowd-sourced road alerts, feasibility proposal

Status: research and architecture proposal, 2026-09-29. No JBV1 feed, third-party alert API, gauge display path, or live phone-to-gauge transfer is implemented or qualified here. This feature is tracked as [ALERT-EXT-001](../roadmap.md#external-crowd-sourced-road-alerts-proposed-extension).

## Observed product behavior and access boundary

[JBV1's publisher listing](https://play.google.com/store/apps/details?id=com.johnboysoftware.jbv1) describes an Android companion for Valentine One detectors, using the detector's Bluetooth connection for radar data. It advertises GPS marks, red-light and speed-camera locations in the USA/Canada, location-based lockouts, alert persistence/logging, and an Internet-dependent map view of logged alerts. The reviewed listing does not establish the current origin, format, or availability of JBV1 crowd reports. A dash integration must distinguish **detector observations**, **stored location marks**, and **crowd reports** rather than present them all as live verified hazards. The listing is evidence of user-facing behavior, not an external JBV1 event API or iOS app. No documented JBV1 API, BLE alert export, or data redistribution permission was found in the public materials reviewed. Ask John Boy Software for an interface and terms before committing to JBV1-specific work.

Waze is an example of a crowd source, but its [partner data-feed documentation](https://developers.google.com/waze/data-feed/overview) describes partner submissions into Waze; it is not a general grant to read or redistribute live Waze reports. Its [partner help](https://support.google.com/waze/partners/answer/10618035?hl=en) describes crowd incidents and reliability/confidence signals. Do not derive an unlicensed product feed from app traffic, map scraping, notifications, or an undocumented endpoint. Source availability and permitted display/retention need explicit verification for each provider and region.

## Integration paths

| Path | Flow and potential value | Feasibility and main limits |
| --- | --- | --- |
| Direct gauge BLE to detector or JBV1 | Gauge connects to a Valentine detector or hypothetical JBV1 BLE service; no phone relay in the display path | Low for crowd data. Detector BLE carries detector observations, while Internet crowd data lives on the phone. No JBV1 export service is documented. Another central link competes with up to two OBD links plus companion, so require radio measurements and documented protocol rights before any spike. |
| Android companion bridge | Authorized JBV1/provider event source -> Android eGauge -> authenticated gauge BLE -> small overlay | Best first transport experiment. It reuses the owner connection and needs no gauge Internet setup. A JBV1-to-app bridge still requires an authorized API or explicit share intent. Android notification access is technically possible via [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService), but notification text is incomplete, user-sensitive, format-unstable, and unsuitable as the product feed. Background BLE work has [lifecycle restrictions](https://developer.android.com/develop/connectivity/bluetooth/ble/background). |
| iOS companion bridge | Licensed/provider feed -> iOS eGauge -> authenticated gauge BLE | Viable with a source accessible to the iOS app; JBV1 is Android-only in the reviewed publisher listing. [Core Bluetooth background modes](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html) can wake for BLE events, but do not guarantee continuous Internet fetching or permanent execution. Test locked phone, navigation foreground, reconnection, and state restoration on a real iPhone. |
| Cloud microservice | Licensed source -> server normalizes, deduplicates and applies TTL -> phone -> gauge | Useful if a provider requires server credentials, multiple regions/sources, or shared normalization. Adds hosting cost, outage/security duties and precise-location privacy risk. The gauge should not connect directly to a cloud service by default: it has no cellular data, and vehicle Wi-Fi availability/radio coexistence are unproven. A microservice does not create rights to JBV1/Waze data. |
| Hybrid | Phone owns location, route context and BLE; optional server supplies authorized nearby events and static camera database updates | Preferred long-term shape if licensed data exists. Phone can cache bounded static marks for short offline gaps, while time-sensitive reports expire. Server is optional; the same versioned alert contract serves local fixtures and permitted direct provider APIs. |

## Proposed event boundary and gauge behavior

Add an **external road-alert** namespace beside, not inside, the local `alert_engine`. The companion fetches only from a permitted source, normalizes events, decides relevance using phone location/heading or route where authorized, and sends a bounded nearby set. Proposed envelope: `schemaVersion`, source and permitted attribution, opaque event ID, category, coordinates or distance/bearing, source observation time, phone receipt time, expiry/TTL, confidence if supplied, sequence, and phone location age/accuracy. Do not invent a confidence score when absent. The gauge derives remaining life from received TTL and its monotonic clock; reject duplicate/out-of-order, malformed, oversized and expired messages. Do not compare its clock directly with phone wall time.

Use the existing owner-authenticated gauge GATT session and a separately capability-gated characteristic/command. Limit event count, payload size, update rate and display interruption rate. External updates are best-effort and must not block OBD polling, configuration, OTA, or local warnings. Show a short category and distance with clear source attribution and an age indicator inside the round display's safe area. Critical local OBD alerts and MIL remain higher priority. A road report disappearing or phone disconnecting produces `unavailable` or expiry, never a successful clear of a local vehicle alert. Avoid flashing and require no interaction while driving. The phone can show fuller source details when parked.

Retention should default to a short-lived in-memory cache on the gauge. Do not store exact location or journey history on the gauge. Make phone location sharing opt-in and minimize server queries to the provider's licensed need; document retention and deletion before any hosted pilot. Keep source attribution and region/license limits in the UI and telemetry. The gauge must remain fully useful with no phone, Internet, JBV1, or external feed.

## Feasibility gates and recommendation

1. **Source rights and data shape:** request JBV1 developer documentation/permission and examine licensed alternatives. Verify categories, timestamps, expiry, location accuracy, usage limits, attribution, geographic coverage, and whether redistribution to a separate gauge is permitted. If no authorized source exists, stop live-feed work after the synthetic UX/transport experiment.
2. **Phone-to-gauge contract:** implement a fixture-driven Android vertical slice, then matching iOS parsing and visual states. Measure event-to-display latency, lost/duplicate events, old-event rejection, reconnect recovery, battery impact and two-OBD-adapter plus phone operation. Use the existing [three-link radio gate](multi-adapter.md) and separate actual physical observations from simulations.
3. **Source pilot:** connect one permitted source through the phone. Test stationary/moving relevance, direction, repeated reports, false positives, coverage gaps, no data, app background/phone lock, and loss of Internet. Never imply that an absent report proves a clear road.
4. **Backend decision:** add a microservice only for a concrete provider/authentication or multi-source need, with an owner, cost ceiling, monitoring, rate limits, abuse controls, and location-retention policy. Otherwise keep direct phone fetching. Promote public capability only after Android and iOS physical acceptance and source-rights review.

Recommendation: start with the phone-to-gauge event contract and labeled synthetic events after M4, while pursuing an authorized provider. This tests the product experience without coupling firmware to JBV1 internals. A hybrid phone plus optional microservice is the likely live architecture if a licensed feed becomes available; direct detector BLE is a separate radar-detector product scope and should not be treated as the crowd-alert path.
