Action pages: proposed interaction contract

Review 1 · 19 October 2026 · awaiting owner approval. No runtime changes. The gallery's per-screen notes and this contract are part of the version-bound approval.

Information architecture

Reading pages and action pages are sibling collections under one gauge assignment. The vehicle profile supplies compatible action definitions and parameters. Each assigned gauge chooses its action pages and order. An optional TCM remains a child transport; it does not create another menu or action tree.

Gauge tab → selected gauge → Action pages → Add/Edit/Remove/Reorder → existing acknowledged configuration transaction. Action setup belongs here, not under Expert. Expert retains controller-level diagnostics.

Navigation and gestures

  • Reuse the existing screen-oriented recognizer and configured upward sequence, default three distinct strokes within five seconds. Show unobtrusive progress after the first stroke; cancel on timeout, wrong direction, overlay, assignment change or touch cancellation. Do not introduce another recognizer. A single upward swipe can be a future configurable entry choice, never a hidden shortcut change.
  • Completion enters the first action page, or the active action if one needs attention. Left/right swipes browse without wrapping past an unsafe confirmation. Dots denote position; no mixed reading/action dots. One action page has no dots. More than five pages uses a bounded numeric position instead of crowded dots. Review examples use three pages.
  • Swipe down or tap the top chevron returns to the exact originating reading page, with cached fresh values populated immediately. Confirmation Back cancels to its action page first. No control operation runs on entry, swipe, hold or exit.
  • Retain the existing hold/pairing gesture on ordinary reading pages only. Within actions, a hold does not open pairing or start a command. Suppress clicks after recognized swipes; use press/release hit regions with cancellation outside the button. Pairing/update overlays own input exclusively.
  • Pause automatic page cycling throughout the action branch. On return, resume a fresh full interval; do not advance immediately because a timer expired while away. With no active operation, return to readings after 30 seconds without input; never time out a confirmation into execution. With an active or uncertain operation, remain until the user exits. These proposed timings need review and physical qualification.

Execution and restoration

StatePresentation and next step
ReadyAction name, meaningful duration or current state, one Start control. Known missing protection has an inline setup reason. Unknown/stale inputs mean Waiting for car, never Ready.
ConfirmationNamed purpose plus duration/impact. Start revalidates the running assignment and fresh controller preconditions. ABS/TCS confirmation must say an ignition cycle may be needed to restore. A cancelled confirmation sends nothing.
Starting / ActiveNo optimistic success. Show Starting until verified; then countdown. Stop is a direct 44 px minimum control with no second modal. Multiple taps cannot queue duplicate operations. No arbitrary RPM editor: current captured behavior is a fixed raised-idle setting.
Stopping / StoppedKeep Stopping until independent restoration evidence. Stopped is a retained outcome, not an automatic restart. Duration expiry and thermal protection use the same command owner.
UnknownRetain the uncertainty and recovery context. Reconcile reads before any Retry Stop write; no replay after a lost response, reconnect or boot. Check idle is a concrete instruction, with detailed ignition guidance in the App.
ABS/TCS OffRestore is a desired-state request, not a claim the dash lamps cleared. Preserve Off/Unknown and parked ignition-cycle guidance until independently confirmed. Do not conflate this with Line Lock.

Coolant protection uses the existing primary ECM high-coolant alert, confirmed running configuration and fresh direct readings. Missing threshold blocks Start. Heat or stale/invalid required coolant while active latches Return. Never automatically restart after cooling. The App links to the existing coolant alert editor rather than creating another setting.

Layout and content guardrails

  • 240 × 240 logical pixels. Production Noto Medium/SemiBold, existing color tokens, black gauge face. Essential text and full button rectangles fit radius 112; art generator checks bounds. This proposal follows the expanded production envelope, not the older radius-104 historical calibration. Physical edge clipping and touch accuracy still require validation.
  • Top return control has a 44 × 44 logical target centered near (120, 32). CEL icon/count stays in the reserved upper status band, action name near y67, main value/status y98–130, primary control y145–189, alert reason near y193, position dots near y212. One owner composes all bands. No duplicate units or generic success prose.
  • Green denotes an available primary control or confirmed active state, amber caution, red critical. Do not rely on color alone. Critical attention uses the shared alert owner and may preempt the branch. Acknowledge returns to the current action without restarting it. Protective Stop runs even if a critical screen is visible.
  • Labels are validated against the actual chosen font and available chord width, not a character count alone. App preview recommends a short name, maximum 20 graphemes; names that still do not fit must be edited. Never silently truncate action identity or shrink below 16 px on the gauge. No scrolling safety instructions. Long help belongs in the App.
  • Future action definitions provide a stable ID, localized short name, typed bounded parameters, current-state vocabulary, primary/stop labels, qualification requirements and restoration semantics. Reject unsupported states/parameters. Never accept raw packets or arbitrary scripts from a page definition. Future music/navigation content belongs to its existing content interface, not a vehicle command shim.
  • Full values never wrap or truncate. Unsupported controller actions remain outside the normal picker. Already configured but no longer compatible actions stay visible as unavailable with removal available in the App; they cannot execute.

App workflow

One list, in gauge order. Tapping a row edits it; its overflow contains Move up, Move down and Remove with Undo. Add lists compatible definitions with plain descriptions and disables already-added items. The same shared connection pill remains in the header. Save offline is explicitly Saved on phone; only verified configuration readback becomes Saved to gauge. Removing the active action is disabled until it has stopped or its uncertain outcome is resolved. Removing a page never hides an unresolved operation.

Minimal implementation after approval

  1. Add a bounded ordered typed action-page collection to the existing vehicle/gauge assignment model, with explicit schema/version migration. Preserve existing local page-jump bindings. Migrate a legacy Vehicle actions binding to the new collection only when its definitions/parameters are valid; otherwise show the empty setup page. Existing gesture counts stay unchanged.
  2. Replace only the flat gauge command menu presentation with a paged branch. Keep its existing command owner, worker arbitration, cancellation, duplicate suppression, cooling/Stop logic and scoped states. Render current snapshots, not another polling worker or retained LVGL screen for every configured page.
  3. Expose App list/add/edit using existing cards, shared pill, durable writes and acknowledged apply. Add no dependency, new transport or per-action persistence owner.
  4. Test entry recognition, orientation transforms, exact reading return, cycling pause/resume, repeated taps, active navigation, missing data, threshold changes, source loss, critical priority, boot reconciliation, configuration migration and independent ECM/TCM continuity. Run native LVGL frame/glyph checks and allocation/stack checks. Then qualify physical gestures and parked Start/Stop/restoration separately.

The review-only Open actions button skips gesture entry for quick inspection; it does not change the proposed physical entry gesture. The interactive prototype exercises Air up entry, confirmation, active navigation, Stop, thermal protection and lost connection.
